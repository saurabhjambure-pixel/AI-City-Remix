## 0. Non-negotiable rules for the coding agent

1. **M3.1 decides; you build.** All research, claims, verification judgements, the script, scene HTML, frame review and the end-card content come from `minimax/minimax-m3.1-flash` through `https://api.sandbase.ai/v1/chat/completions`. You write infrastructure code only.
2. **Never hand-write or hand-edit generated content** (claims, script, scene HTML, review verdicts). If output is bad, change the *prompt* or the *pipeline code* and rerun. Every exception the owner approves is logged with `python log_edit.py "<reason>"`.
3. **No mocks in real runs.** No placeholder HTML, no fallback content generated by you. If the API is unreachable or the key is missing, stop and report. Mocks are allowed only in unit tests and must be clearly named `fake_*`.
4. **Credentials:** read `SANDBASE_API_KEY` from `.env` or the environment only. **Do not search the home directory, shell history, or other apps' config files for keys.** Never print, log or commit the key. `.env` is in `.gitignore`.
5. **Every model call is logged** to `runs.jsonl`: timestamp, stage, scene id, reasoning_effort, max_tokens, HTTP status, latency, `usage` (including `completion_tokens_details.reasoning_tokens`), and output file path.
6. **Always set `reasoning_effort` explicitly** per stage (table in §3). The API default is `max`, which is slow and can drift off-brief.
7. **Keep the full assistant message** (including `reasoning_content` and `tool_calls`) in history across tool turns.
8. **Resumable.** Every stage writes its artifact to `output/<city>/` and is skipped on rerun if the artifact exists and validates, unless `--force <stage>` is passed.
9. **Contest constraints are code-enforced** (§7), not left to memory.

## 3. Stage specifications

### Shared: `sandbase_client.chat()`
- Arguments: `stage`, `messages`, `effort` (required, no default), `max_tokens`, `tools` (optional), `response_format` (optional), `scene_id` (optional).
- `max_tokens`: 128000 for scenes and endcard; 32000 for the other stages.
- Timeout 900 s. Retry twice on 429/5xx/timeout with backoff (10 s, 40 s). Do not retry a 4xx other than 429.
- JSON outputs: ask for JSON only, strip fences, parse, validate against `schemas/`. If invalid, send one repair turn ("Your output failed validation: <errors>. Return corrected JSON only."), then fail the stage.
- Images: `{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}}` inside `content`.

### Stage 1 — research (M3.1 + tools, effort `high`)
Tools exposed to M3.1:
- `web_search(query, engine)` → SandBase search endpoints. Discover exact endpoint names and input schemas once with `npx -y @sandbaseai/cli@latest discover` / `inspect` (inspect is free). Expected engines: Tavily, Exa, Scholar. Record names and per-call prices in `tools/search.py`. If SandBase search is unavailable, fall back to the Wikipedia search API only, and say so in `PROGRESS.md`.
- `fetch_url(url, offset=0)` → GET with a descriptive User-Agent; extract readable text (BeautifulSoup); cache to `sources/<sha1>.txt` with url + fetch time; return 30k chars from `offset`.
- `save_claims(claims)` → writes `claims.raw.json`.

Budget: at most 60 search calls and 80 fetches per city. Target 40–60 raw claims across these clusters: geography/rivers, origins, Maratha era, Peshwa era, British/cantonment, education ("Oxford of the East"), industry, IT growth, culture/food/monsoon.

Each claim **must** carry ≥1 source with a **verbatim quote** copied from the fetched text.

### Stage 2 — verify (code check + M3.1 judge, effort `xhigh`)
1. **Code (deterministic):** for each source, re-read the cached text and confirm the quote appears in it (normalise whitespace and case). Drop sources that fail.
2. **Code:** count independent sources = distinct registrable domains, treating Wikipedia mirrors as one.
3. **M3.1 judge:** for each claim plus its surviving quotes: `{"supported": true|false, "reason": "...", "corrected_claim": "..."|null}`. A correction may only narrow the claim to what the quotes say.
4. **Keep rule:** judge-supported **and ≥2 independent publishers for every claim** (registrable domains via `tldextract`; Wikipedia family = one publisher; web.archive.org snapshots count as the archived site). Supersedes the earlier 3-source rule for dates and numbers (CLAUDE.md §4A). Before judging, claims with <2 publishers get a corroboration pass (M3.1, ≤3 searches each). Quotes must be complete sentences; date/number quotes must contain the claim's value.
5. Write `claims.json` (kept only) and `research-report.json`: `{total_raw, kept, dropped, independent_publishers, single_source_claims: 0, providers_used}`.

Acceptance: ≥25 kept claims; `single_source_claims == 0`; every kept quote passes the code check.

### Stage 3 — mapdata (code only)
- Overpass (`https://overpass-api.de/api/interpreter`), cache responses.
- Layers: the city's municipal boundary (look up the relation by name and admin level and confirm it is the city, not the district), the Mula and Mutha rivers, and point locations for every place named in `claims.json` (forts, wadas, cantonment, colleges, Pimpri-Chinchwad, Hinjewadi, etc.).
- **Never fetch or draw national or state borders.**
- Simplify geometry (shapely, tolerance tuned so the total is under 40 KB), project to a fixed 1920×1080 viewBox with a padded bounding box, and write `svg_paths.json`: `{layer_id: {"d": "...", "label": "...", "x": .., "y": ..}}`.
- M3.1 gets ready-made path strings, so it never invents geography.

### Stage 4 — script (M3.1, effort `high`)
- Input: `claims.json`, the list of available map layers, a target of 150 s, 7–8 scenes.
- Voice: the city speaks in the first person ("I am Pune…").
- Every narration sentence cites the `claim_ids` it relies on. **Code check:** every cited id exists in `claims.json`; reject sentences with factual content and no citation.
- Scene skeleton (M3.1 may reorder or merge, but must keep scene 1, the close and the end card):

| # | ~Seconds | Content |
|---|---|---|
| 1 | 12 | Cold open at the river confluence: "I am Pune." |
| 2 | 23 | Maratha seat: Lal Mahal, Shaniwar Wada; one line on Bahirjee Naik if verified |
| 3 | 20 | Peshwa capital to British rule; cantonment appears |
| 4 | 20 | "Oxford of the East": colleges bloom across the map |
| 5 | 25 | Industry, then IT: Pimpri-Chinchwad, Hinjewadi; area grows by era |
| 6 | 25 | One warm thing: monsoon on the Sahyadri edge, or the city's food |
| 7 | 20 | Personal close, voice only: "Someone new is putting down roots here…" over an empty plot at first light |
| 8 | 10 | End card (stage 9) |

- Rules in the prompt: no real living people named or shown; no copyrighted material; only verified claims; no borders.

### Stage 5 — tts (SandBase TTS model)
- Discover a TTS endpoint via the SandBase CLI (`discover` with type audio/tts, then `inspect`). Prefer a calm, warm English voice. Record the endpoint name in `stages/tts.py`.
- One WAV per scene. Measure the duration with ffprobe. Scene duration = narration + 0.8 s tail (end card: fixed 10 s, no narration or a single line).
- Subtitle cues: split narration into sentences; assign each cue a time proportional to its character count within the measured duration. Write `timing.json` and the final `.srt`.
- If no SandBase TTS is available, **stop and ask the owner** (fallback options: macOS `say`, or a silent film with subtitles only).

### Stage 6 — scenes (M3.1, effort `medium`, parallel)
- Run up to `--workers` scenes concurrently. Expect minutes to an hour each.
- Prompt template (official format, filled by code):

```
Build scene {id} of a documentary about {city} as ONE self-contained HTML file at 1920x1080.
Look: deep ink background (#0f1115), saffron (#f2a33a) for the city and growth, cream (#f3ead8) labels,
river blue (#5fa8d3). Bold strokes (>= 4px), large type (labels >= 34px, subtitles 44px).
Duration: exactly {seconds} s. Autoplay on load, no interaction, no loop, hold the last frame.
Timeline: {beats with exact times}
Subtitles: bottom-center, max 2 lines, semi-opaque backing, at exactly these times: {cues}
Map: use ONLY these SVG paths and positions (already projected to 1920x1080): {svg_paths subset}
Label only these places: {labels}. Do not draw any country or state borders.
Rules:
- Inline SVG + CSS animation; JavaScript only for timing. No external assets, fonts, images or CDNs.
- Fill the viewport, no scrolling.
- Before finishing, check the page has zero console errors.
- Return only the complete HTML, from <!doctype html> to </html>, with no abbreviation.
```

- Save the model output verbatim (fences stripped). **Code check:** contains `<html`, contains no `http://`/`https://` references to external resources, is under 2 MB.

### Stage 7 — record (code)
- `node scripts/record.mjs scenes/{id}.html video/{id}.mp4 {seconds} 1920 1080`.
- Check with ffprobe: duration within ±0.3 s of target, 1920×1080, h264. Re-record once on failure.

### Stage 8 — review (M3.1 vision, effort `medium`, max 2 rounds)
- Extract frames at 20%, 55% and 90% of each scene. Send them with the scene spec and subtitle cues.
- M3.1 returns JSON: `{"pass": bool, "issues": [{"frame": "...", "problem": "...", "severity": "high|low"}], "prompt_additions": "..."}`.
- On fail with any high-severity issue: regenerate the scene with `prompt_additions` appended, re-record, review again. Stop after round 2 and keep the best version (fewest high-severity issues).
- Typical issues to ask about: unreadable or overlapping subtitles, labels off-screen, blank frames, wrong place labels, nothing moving.

### Stage 9 — endcard (M3.1, effort `low`)
- Inputs from `research-report.json`: kept claims, independent publishers, `0 single-source claims`, plus "Directed by MiniMax M3.1 flash via SandBase", the repo URL and "Run it on your city".
- Same HTML rules as scenes; 10 s.

### Stage 10 — assemble (code, ffmpeg)
1. Per scene: mux video + narration; pad audio with silence to the video length.
2. Concatenate all scenes in order (concat demuxer, same codec params) → 1920×1080, 30 fps, H.264 `yuv420p`, AAC 48 kHz, `+faststart`.
3. Optional music bed: only if generated (SandBase music model) or verifiably licensed for reuse; duck it to about −20 dB under narration. **No copyrighted music.** Otherwise ship narration only.
4. Loudness normalise to about −16 LUFS (`loudnorm`).
5. Subtitles are already burned into the scenes; also write `final/{city}.srt` for the upload page.

### Stage 11 — check (code) → `final/check.json`

| Check | Rule |
|---|---|
| Duration | 60–180 s (target 140–165) |
| Resolution | ≥1280×720 (target 1920×1080) |
| Container/codec | MP4, H.264 video, AAC audio |
| Subtitles | present in every scene (from the scene spec) |
| Claims | every narration sentence with a fact cites a kept claim |
| Sources | `single_source_claims == 0` |
| Borders | no national/state boundary layer was fetched or passed to any scene |
| Assets | no external URLs in any scene HTML |
| Manual edits | count from `runs.jsonl`, reported (target 0) |

The film is uploadable only when all checks pass.

## 5. System prompts (write to `prompts/`, tune by rerunning, never by editing outputs)

- **research.md:** "You are a meticulous researcher building a fact base for a short documentary about {city}. Use web_search and fetch_url. Prefer original and official sources: government, universities, archives, museums, peer-reviewed work, then reputable press, then Wikipedia. Every claim must include a verbatim quote copied exactly from a page you fetched. One fact per claim. No claims about living people. Stop when each cluster has 4–8 well-sourced claims or the budget is spent. Save with save_claims."
- **verify.md:** "You are a fact-checker. For each claim, decide only from the quotes given whether they support the claim. If they support a narrower version, return that as corrected_claim. Never use outside knowledge to support a claim. Return JSON only."
- **script.md:** "Write a ~150-second first-person documentary script in which {city} speaks about itself. Warm, specific, unhurried; short sentences that read well aloud. Use only facts from claims.json and cite claim_ids for every factual sentence. No living people. Follow the scene skeleton. Return JSON matching the schema."
- **review.md:** "You are a strict film editor reviewing 3 frames from a 1920x1080 scene against its spec. Flag only real, visible problems: unreadable or overlapping text, elements cut off, blank or frozen frames, wrong labels, a missing subtitle. Return JSON only."
